# Длинные записи: час и больше

## Итог

`SherpaVadTranscriber` читает WAV кусками по 0,5 с прямо в пайплайн, а не
целиком: память не зависит от длины записи, лимит — 12 часов (раньше 60 минут,
и уже на часе ~230 МБ Java heap под аудио). Перекластеризация спикеров на сессии
больше 600 реплик (час-полтора речи) больше не сливает разных людей.

Запись на 76 минут — 24 живых диалога подряд (три актёра M/D/S во всех файлах),
эмулятор, режим файла, e2e RNN-T:

| | 24 файла по отдельности | одна запись 76 мин |
|---|---|---|
| WER | 3,70 % | **3,66 %** |
| ошибка атрибуции | 1,8–2,4 % (отображение спикеров в каждом файле своё) | **2,4 %** (одно на весь час) |
| спикеров | верно в 23 из 24 файлов | **3 из 3** |
| RTF | 0,22–0,24 | 0,18 |
| PSS | ~530 МБ в конце | 570–700 МБ весь прогон, без роста |

В записи 682 реплики — больше порога 600, так что работал новый путь
перекластеризации. Время обработки 13,9 мин на 76 мин аудио.

## Что было не так

- **Чтение целиком.** `WavReader.readMono16k` клал весь файл в `FloatArray`:
  3,84 МБ на минуту в Java heap. Лимит 60 минут, и даже он на телефоне с кучей
  256 МБ на грани `OutOfMemoryError`.
- **Склейка на длинной сессии.** Больше 600 реплик — соседние склеивались по
  онлайн-метке, а если метки чередовались, то просто подряд, без проверки
  сходства. На синтетической сессии из 20 000 реплик трёх голосов с неверными
  онлайн-метками прежний код сливал всех в одного спикера (верно 33,6 % реплик),
  на 2 000 репликах — 80,6 %. Сейчас — 100 % в обоих случаях.
- **Скорость слияния.** На каждом шаге заново считалось сходство всех пар —
  O(n³·dim). Теперь сходства кешируются, у строки хранится лучший партнёр.
  На сессиях до 600 реплик результат совпадает с прежним один в один
  (JVM-тест сравнивает с копией старого алгоритма на случайных сессиях).

## Что вне `:speech`

- На Android 15+ сервис обработки идёт с типом `mediaProcessing` — у него
  системный лимит 6 ч в сутки; wakelock приложения тоже на 6 ч. Для записей до
  1,5 ч (обработка ~15–20 мин) это не мешает.
- Если процесс убит посреди обработки, сессия становится `INTERRUPTED` и
  начинается заново — на длинной записи это потеря всей работы.
