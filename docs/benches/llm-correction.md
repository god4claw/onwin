# Коррекция расшифровки

Дата: 2026-11-07. Ветка `llm-onwin` (копия `private-onwin`).

Одно изменение в `:speech` — **постобработка текста**: словарная и LLM-коррекция
ослышек отдельной стадией после сессии, а не внутри неё.

Декодер не трогали: остаётся `greedy_search`. `modified_beam_search` для NeMo-CTC
в sherpa-onnx 1.13.0 роняет процесс нативным abort; для RNN-T (`AsrModel.E2E_RNNT`,
модель по умолчанию в `onwin`) он возможен, но это отдельная задача с замером WER
и RTF — [`bench-decoding.md`](bench-decoding.md).

## Постобработка

### Зачем

Правка ослышек и опечаток в словах: «иванофф» → «Иванов», «придёт» → «приедет»,
«кубернетес» → «Kubernetes». Это не «причесать речь»: ошибки самого говорящего
трогать нельзя — эталон сравнивается с вербатимом, и «исправление» грамматики
повышает WER.

### Слои

| Слой | Класс | Что делает | Цена |
|---|---|---|---|
| 0 | `LexiconCorrector` | точная замена по словарю, сохраняет регистр | ~0 мс, 0 МБ |
| 1 | `LlmCorrector` | правка через локальную LLM с гардом и масками | 0,5–1 с, ~450 МБ |
| — | `CompositeCorrector` | цепочка слоёв по порядку | — |

Слой 0 закрывает имена и термины — то, что LLM делает хуже и дороже.
Слой 1 имеет смысл только если A/B покажет прирост WER.

### Где запускать

`TranscriptPostprocessor.process(segments)` — **после** конца сессии и после
`release()` движка распознавания:

```
stream/batch → Done(segments) → release() ASR → postprocess → экспорт
```

Причины:

- ASR держит в памяти GigaAM (~305 МБ) и embedding-модель; LLM рядом — ещё
  ~450 МБ, на 4-ГБ телефоне такой пик в момент записи заканчивается убийством
  процесса вместе с незаписанным аудио;
- `Done` пересобирает сегменты (`SpeakerReclusterer` + `mergeSameSpeakerNeighbors`):
  спикеры перенумеровываются, соседние реплики склеиваются. Правки, сделанные
  до этого момента, частично уедут в склеенный текст, частично потеряются.

Последовательно пик остаётся на уровне текущего: ~640 МБ в распознавании,
~500 МБ в коррекции.

### Защита от порчи текста

- `EntityMasking` — числа и проценты на время генерации заменяются
  плейсхолдерами `[[0]]`; потерянный или придуманный плейсхолдер отбрасывает
  весь ответ.
- `CorrectionGuard` — правка больше 10 % символов (по нормализованному тексту)
  считается переписыванием и откатывается к исходному.
- `LlmCorrector.budgetMs` — бюджет времени на реплику; не успел, упал, вернул
  мусор — текст остаётся исходным. Исходный текст всегда валиден.

### Подключение рантайма (сделано)

`:speech` не тянет нативный рантайм: он весит десятки мегабайт и собирается
под каждый ABI. Приложение подставляет `TextGenerator` — и это уже не пример,
а модуль [`../../llm`](../../llm/README.md):

- `OnnxGenAiGenerator` реализует `TextGenerator` поверх ONNX Runtime GenAI
  (AAR 0.19.0 в `../../llm/local-repo`, ядро ORT 1.31.1);
- модель Qwen2.5-0.5B-Instruct (ONNX GenAI, int4) ставится отдельно скриптами
  `../../llm/scripts/fetch-model.ps1` и `llm/scripts/push-model.ps1` — в APK её нет;
- `OnDeviceLlm.create(context)` собирает на одной модели проходы:
  `corrector` (`CompositeCorrector`: словарь + `LlmCorrector`), `analyzer`
  (`LlmDialogueAnalyzer`: имена спикеров и резюме) и опциональный
  `protocolAnalyzer` (протокол по кнопке). Язык RU/EN/MIXED выбирает промпт;
  на английском корректор не запускается. Нет модели — `null`.

```kotlin
// AppBindings: модель есть — оба прохода будут, нет — этап пропускается.
val llm = OnDeviceLlm.create(context)

DefaultProcessingController(..., corrector = llm?.corrector, analyzer = llm?.analyzer)
```

Порядок в очереди задан в `DefaultProcessingController.correct()`:
`Done` ASR → `Transcriber.release()` → `CORRECTING` в статусе и прогрессе →
правка реплик (0…70 %) → разбор диалога (70…100 %) → `DONE`.
Модель живёт до конца пачки и выгружается вместе с ASR.

Разбор диалога — `LlmDialogueAnalyzer`:

- диалог режется на куски по 3 000 символов, имена собираются по всем кускам:
  имя, названное один раз в середине разговора, иначе не найти;
- имя принимается, только если не спорит с другими кусками (при равенстве
  голосов — отказ);
- резюме валидируется: эхо расшифровки («Спикер 1: …»), текст без букв нужного языка,
  короче 40 символов и с `|` отбрасываются;
- результат сохраняется в Room (`session_notes`, `speaker_suggestions`) и виден
  на экране записи: «Кратко» и чипы «Спикер N — Имя».

Обещание «LLM проверяет отмену на каждом токене» выполнено:
`OnnxGenAiGenerator.generate` вызывает `ensureActive()` перед каждым
`generateNextToken`, поэтому `withTimeoutOrNull` в корректоре и анализаторе
реально останавливает генерацию.

На финальном проходе бюджет щедрее (5 с на реплику): спешить некуда, а обрыв
на середине хуже ожидания.

### Кандидаты модели

| Модель | Размер | Русский | Комментарий |
|---|---:|---|---|
| Qwen2.5-0.5B-Instruct, ONNX int4 | ~0,9 ГБ | да | **выбрана**: грузится на эмуляторе, ответ на реплику ~10–15 с |
| Qwen3-0.6B | ~400 МБ (GGUF) | да | нужен `enable_thinking=false`, иначе ответ уходит в рассуждения |
| Gemma-3-1B | ~800 МБ | да | следующий шаг, если 0.5B не хватает |
| Llama-3.2-1B | ~800 МБ | **нет** | не брать: русского в списке языков нет |

### Проверено на устройстве

Pixel_8_API36 (x86_64, Android 16), 2026-11-07, `:llm:connectedDebugAndroidTest`:

- `OnnxGenAiGenerator` грузит модель и возвращает кириллицу;
- полный `LlmCorrector.correct("я придёт завтра в девять")` возвращает исходный
  текст: модель 0.5B без примеров в промпте переписывала фразу по смыслу
  («я буду работать завтра в десять»), с двумя примерами — повторяет дословно;
  в обоих случаях `CorrectionGuard` не дал испортить расшифровку;
- значит, инфраструктура работает, а выигрыш по WER ещё надо доказать на
  эталонных репликах (см. «Как проверять»).

## Как проверять

Стенд уже есть — `../../speech/BENCHMARK.md`, золотой набор
(`bench-golden-baseline.md`). Порядок:

1. Прогнать golden set как есть, записать WER и spkErr (базовая точка: 16,0 % /
   11,5 %).
2. Взять 20–30 реплик с ручным эталоном, прогнать через корректор, посчитать
   WER до/после.
3. **Критерий приёмки:** WER упал хотя бы на 1 п.п. Если нет — LLM не
   подключается, в отчёте фиксируется отрицательный результат.

## Ограничения

- Все замеры выше — x86_64-эмулятор. На 4-ГБ arm64-телефоне нужны собственные
  RTF, PSS и секунды на токен.
- Корректор работает по одной реплике и не видит контекст диалога: имена,
  прозвучавшие один раз, он не свяжет между репликами.
- Слой 1 не запускается на устройствах с малым объёмом RAM — это решение
  вызывающего кода, в `:speech` флага памяти нет.
